# 架构：什么该进 SQLite，什么该交给宿主模型

这份文档回答一个具体问题：**一个 Skill 形式的产品，记忆和执行分别放在哪里。**

结论先给：

> **模型负责「听懂」，代码负责「算准」，SQLite 负责「记住」。三者不能互换。**

---

## 一、为什么必须分开

一个反例就够了。如果把"用户今晚喝酒了，明早不要冰饮"这句话直接丢进模型，让模型在每次推荐时"记得"它，会发生三件事：

1. 今天记得，明天上下文一换就忘了；
2. 同一句话问两次，可能给出两种理解；
3. 忘了的时候**不报错**，静默地推荐一杯冰咖啡。

第三件事最致命。它不会崩，只会安静地做错。而早餐是每天一次的，错三次用户就不用了。

所以判断标准不是"这个功能适合放在哪"，而是：

| 问题 | 归谁 |
|---|---|
| 这个结果必须每次一模一样吗？ | 是 → 代码 / SQLite；否 → 模型 |
| 这个结果事后要能被查出来"为什么"吗？ | 是 → SQLite |
| 这个结果只能靠语义理解得到吗？ | 是 → 模型 |
| 这个结果一旦错了，会花钱或伤身体吗？ | 是 → 代码，且要有硬否决 |

---

## 二、三层分工表

### 第 1 层：SQLite（`scripts/db.py`）

**只存确定性事实。不存模型的自由解释。**

| 表 | 存什么 | 为什么必须落库 |
|---|---|---|
| `profile` | 目标、预算、热量区间、门店、地址、喜欢/忌口、非本餐段品类词、身体信息 | 每次决策都要读，且用户改一次要永久生效 |
| `meal_log` | 三餐记录：日期、餐段、食物、**热量区间上下界**、来源、置信度 | 要能按日期范围查、按来源过滤、算衰减 |
| `context` | 临时情境：喝酒、熬夜，**带失效日期** | 关键：`applies_to` 一到就自动不参与，绝不残留 |
| `feedback` | 好吃/不好吃/量不够 | 这是"好吃"唯一可计算的来源 |
| `orders` | 真实订单：原价、抵扣、实付、`comboItemList`、`couponList`、支付窗口 | **唯一和"真付了钱"对齐的事实** |
| `coupon_snap` | 券快照：couponId、couponCode、绑定商品码、有效期 | 券绑定具体商品，必须能按 productCode 反查 |
| `menu_snap` | 菜单快照：菜单价、真实核价、热量、来源 | 价格会漂移，要能对比"上次是多少" |
| `plan` | **前一晚算好的决策**，含可直接执行的 create-order 参数 | 「早上自动」全靠它，见第四节 |

为什么不用 JSON 文件？因为要回答这些问题：*"我最近 7 天吃了几次油炸？"*、*"哪些券绑定了这个商品码？"*、*"明天有没有已经算好的计划还没执行？"*。JSON 要全量加载到内存再筛，SQLite 一条 SQL 就够。而且 SQLite 是 Python 标准库，**skill 分发不需要任何额外依赖**。

实测验证（`MCD_BUTLER_HOME=.demo_db`）：

```
summary: {'meals': 1, 'contexts': 1, 'orders': 0, 'plans': 1, 'coupons': 1}
ctx(2026-10-21):  [('alcohol', ['冰','冷萃'])]
ctx(2026-10-22):  []                      ← 过期自动失效，不是靠模型记得
coupon(507411):   ['9.9元中杯冰美式']
coupon(9900005470): []                    ← 粥王套餐没有可用券，不是靠模型猜
```

### 第 2 层：宿主模型（读 SKILL.md 的那个 agent）

**只做四件代码做不了的事，且每件的输出都要能被校验。**

| 职责 | 输入 | 输出 | 校验方式 |
|---|---|---|---|
| 照片识别 | 一张三餐照片 | `[{name, portion, kcal_low, kcal_high}]` + 置信度 | 必须有区间，不许给单点值 |
| 语义抽取 | "今晚喝酒了，明早不要冰咖啡" | `{tags:["alcohol"], exclude:["冰"], applies_to:"2026-10-21"}` | **必须回显给用户确认**，一句话可撤销 |
| 解释生成 | 决策的 `trace` | 人话理由 | 理由必须引用 trace 里的具体条目，不许编 |
| 缺项追问 | 首次设置缺失字段 | 一次问完 | 只问一次，之后不许反复问 |

**模型不做的四件事**（做过就出错）：

1. **不算钱** —— 菜单价是虚标的（组合类实付比菜单价高 67%），只有 `calculate-price` 是真的。让模型"估一下"，每天错几块钱。
2. **不做最终选择** —— 选择必须由 `planner.py` 按固定优先级算，这样同一份账本每次结果都一样。模型介入就会漂移。
3. **不记住偏好** —— 模型记的东西在下一轮上下文里可能就不在了。偏好必须写进 `profile` 表。
4. **不判断"这一餐是否安全"** —— 忌口是硬否决，必须走代码里的字符串穿透检查（含套餐组成）。

### 第 3 层：脚本（确定性计算）

| 脚本 | 做什么 | 为什么必须是代码 |
|---|---|---|
| `mcp_call.py` | MCP 直连 + 混合格式解析 | 返回体是「Markdown 说明 + JSON」拼接，模型每次解析结果可能不同 |
| `resolver.py` | 商品 → 热量（单品直配 / 套餐拆解 / 无数据三态） | 必须严格执行"宁可无数据，不许错配" |
| `planner.py` | 优先级仲裁 | 仲裁顺序要能被审计，不能是"模型觉得" |
| `db.py` | 记忆层 | 见上 |
| `place_order.py` / `live_test.py` | 执行与证据落盘 | 每一步请求/响应/traceId 都要留在磁盘上 |

## 三、数据流：一次完整的决策

```
[照片] ──模型──> {食物, 区间, 置信度} ──代码──> db.meal_log
[一句话] ─模型──> {tags, exclude, 生效日} ──回显──> 用户确认 ──代码──> db.context

                          ↓ 每天决策时读取
db.profile + db.meal_log(近14天) + db.contexts_for(明天) + query-meals + calculate-price
                          ↓
                    planner.py 固定优先级
                          ↓
              pick + trace（含"排除了什么、为什么"）
                          ↓
              db.save_plan (前一晚)  ──> 定时任务 (早上) ──> create-order
                          ↓                                    ↓
                    卡片给用户看                        payH5Url 推给用户
                                                              ↓
                                                    用户点一下完成支付
```

注意这条链上有两个**人类介入点**，它们不是缺陷：

1. **情境抽取的回显** —— 抽错了能被发现。
2. **支付** —— 35 个工具里没有任何支付工具，这是硬边界（见第五节）。

## 四、"前一晚安排好，早上直接吃"怎么做

### 先说实测事实（这条推翻了我之前的假设）

外送预约单同样是下单即 15 分钟倒计时：

| 场景 | 预约时间 | createTime | expirePayTime |
|---|---|---|---|
| 到店外带 | 明早 07:00 | 09:52:22 | **10:07:22** |
| 外送 | 明早 07:30 | 10:27:39 | **10:42:39** |

**预约只锁「什么时候取餐」，不锁「什么时候付款」。** 所以"前一晚 22:00 下单，明早直接吃"在接口层面不成立——订单会在当晚 22:15 作废。

### 所以只能这样做：决策前置，执行后置

```
前一天 22:00          算好 plan，写进 db.plan，**不下单**
                      （菜单、库存、价格此时已能确定到明早时段）

当天 06:40            定时任务执行 plan
                      create-order → 拿 payH5Url
                      → 推送到用户手机（邮件 / 微信）

06:41–06:55           用户起床，点链接付款（15 分钟内）

07:30                 到店外带，或外送上门
```

**这个方案的代价要讲清楚：用户早上要点一下。** 不是"洗漱完就有"，是"洗漱前点一下，洗漱完就能吃"。

这是接口决定的，不是设计选择。任何声称能做到"完全不用管"的方案，都建立在"支付能自动扣款"这个不存在的能力上。

### 具体怎么落地

- 决策前置：`python scripts/planner.py --ledger-from-db --slot breakfast` 输出 plan 并 `db.save_plan()`
- 执行后置：定时任务调 `python scripts/run_plan.py`，它读 `db.due_plans()`，逐条 `create-order`，把 `payH5Url` 发出去，然后 `db.mark_plan(id,'executed',order_id)`

时效性上还有一个必须检查的点：**菜单和券在早上可能已经变了**。所以 `run_plan.py` 执行前必须重跑一次 `calculate-price` 复核金额，金额偏离计划超过阈值（如 +10%）就**不下单**，改为推送"今天有变动，要不要换"。

## 五、支付的真实边界

35 个工具里，**没有任何一个能扣款**。

`create-order` 的完整输出里有 `payId` 和 `payH5Url`，它的 `Next` 字段写得很明确：

> 引导用户："您可以通过支付链接扫码或者打开麦当劳APP完成支付"

也就是说，MCP 的能力止于**生成一张待支付订单**。没有余额、没有免密、没有签约代扣、没有钱包。这不是这个比赛接口阉割，是所有第三方点餐接口的常态——代扣资质不在服务商手里。

所以产品的自动化终点只能是：**预填到支付前一步**。

---

## 六、什么不需要 SQLite

避免过度设计，这几件事不需要落库：

| 事项 | 放哪 | 理由 |
|---|---|---|
| 菜单与价格 | 每次实时查 MCP | 一次查询就够，缓存反而会拿到过期数据 |
| 营养数据 | `data/nutrition.json` | 静态、160 条、不随时间变 |
| 券的可用性判断 | 每次 `query-store-coupons` 实时问 | 券会过期、会下架，本地判断不可靠 |
| 会话内的临时推理 | 模型上下文 | 用完就丢，不需要留痕 |
| 照片原图 | 本地目录，30 天删 | 只留结构化摘要进 `meal_log` |

一条原则：**会变的东西实时查，不会变的打包进仓库，用户的东西放 SQLite。**

---

## 七、一句话总结

- **SQLite 记事实**：吃了什么、说过什么、点了什么、付了多少。
- **模型听懂人话**：照片里是什么、这句话什么意思、为什么这么选。
- **代码算准数**：多少钱、多少卡、能不能下单、要不要否决。

把这三层混在一起，产品会看起来很聪明，然后在某一天安静地给你送一杯你明确说过不要的冰咖啡。
