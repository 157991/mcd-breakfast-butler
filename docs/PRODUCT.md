# 产品定义

一句话定位：

> **拍下三餐，它记住你的口味与饮食，在缓慢减重的目标下，自动安排你愿意吃的麦当劳早餐。**

## 一、场景

工作日，在家洗漱后吃早餐。**固定时间、固定地点，不做每日判断**。
周末与非工作日不在首版范围内。

## 二、六个已拍板的决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 产品形态 | **预填到支付前一步** | `create-order` 返回支付链接，无代扣能力；付款必须由用户本人完成 |
| 减重的角色 | **约束条件，不是目标** | 早餐只影响一天 20–25% 热量，一次饮酒即可抹平一周赤字；承诺体重不诚实 |
| 照片的地位 | **辅助线索，不是核心输入** | 用户明确"懒得拍"；且单张照片误差 ±40%，不足以支撑定量 |
| 首版验收 | **真下单一次跑通全链路** | 只有真实接口能证明"会自动安排"与"会送到"是两件事 |
| 数据主力 | **官方营养库 + 点单历史** | 官方数据可复核；照片与估算只做趋势 |
| 情境规则生效方式 | **回显可撤销** | 抽错一次如果不回显，用户会以为系统坏了却不知道原因 |

## 三、用户不需要做什么

这是本产品最重要的体验标准：**普通的一天，用户不需要作出任何早餐选择。**

| 用户行为 | 系统处理 |
|---|---|
| 发三餐照片 | 自动识别、入账，不要求填表、不追问 |
| 不发照片 | 按长期偏好照常安排，不催、不视为没吃 |
| 偶尔说"明天想吃 X" | 优先满足本次要求，同时检查预算与在售 |
| 说"没吃饱" | 记录反馈，下一次调整搭配；不直接判定"不喜欢" |
| 完全不理会卡片 | 视为同意，按安排执行 |

**只有超出用户事先设定的范围，才打扰他**：超预算、无可选项、门店停业、需要换店。

## 四、决策优先级

```
忌口/过敏 > 当日明确要求 > 情境规则 > 热量区间 > 金额预算 > 好吃 > 不重复
```

完整判定逻辑见 [`references/decision_rules.md`](../references/decision_rules.md)。

## 五、必须承认的局限（写进产品界面，不藏起来）

1. **热量不可能精确。** 官方数据只覆盖 30% 的餐品；照片估算误差约 ±40%。
   所以系统给的是区间和来源标注，不是"精确到个位"的数字。
2. **早餐管不住晚餐。** 早餐一周能省约 1400 kcal，一次饮酒 + 夜宵约 1500–2000 kcal。
   系统知道用户喝酒了（他会拍照），但干预边界只在早餐。
3. **不是医学建议。** 不做营养诊断，不承诺减重结果，"喝酒后不喝冰咖啡"是个人偏好而非健康结论。

## 六、验收标准

分三层，**首版只承诺第二层**。

### L1 能演示（已达成）
- [x] 三个场景（正常 / 稀疏 / 临时要求）均能产出合理安排
- [x] 每个安排都给出 2–4 条用户可验证的理由
- [x] 热量标注来源（官方 / 未知），无官方数据时不伪造数字

### L2 能真实执行（首版目标）
- [x] 菜单、营养、计价全部来自真实 MCP 调用
- [x] 预约时间落在门店实际时段内（实测 06:44–10:15）
- [x] 价格来自 `calculate-price`（分→元），不使用菜单 `currentPrice`
- [ ] `create-order` 跑通一次并成功取消（**待用户授权后执行**）
- [ ] 端到端耗时 < 60 秒（从"安排"到"生成支付链接"）

### L3 长期有效（不在首版范围）
- [ ] 连续 7 个工作日无需用户决策
- [ ] 4 周内"高热量密度餐品替换率"可观测
- [ ] 用户主动修改次数 < 每周 1 次

## 七、明确不做

- 不做饮食打卡应用（用户不想填表）
- 不做全天热量配平（数学上不成立）
- 不做体重承诺（杠杆率不够）
- 不做代扣款（无接口能力，也不该有）
- 不用估算值冒充官方数据（30% 之外就显示未知）
