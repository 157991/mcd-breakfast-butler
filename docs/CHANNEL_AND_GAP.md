> 最近门店 `1450386 麦当劳上海长宁福缘湾九华餐厅`（356 m，淞虹路938号）；
> 预约时点 `2026-10-21 07:30`；全部金额取自 `calculate-price`（单位：分）。

## 一、送到家 / 到店外带 / 取餐柜，到底差多少

先纠正一个说法：**麦当劳没有"外卖柜"。** 接口里的 `takeWayList` 只有三种取值，
这个门店只返回了前两种：

| takeWayCode | 含义 | 谁去取 | 附加费 |
|---|---|---|---|
| `eat-in` | 堂食 | 你在店里吃 | 0 |
| `take-in-store` | 外带 | 你到店里拿了走 | 0 |
| `locker-in` | 取餐柜 | 你自己到店开柜取 | 0 |

**取餐柜也属于到店，不是"送到家"。** 本次的门店不提供取餐柜（`takeWayList` 无 `locker-in`），
只有堂食和外带。外送是完全另一条链路：`orderType=2` + `beType=2`，必须有 `addressId`。

### 同一份早餐，两条链路的真实价格

| 餐品 | 到店外带 | 麦乐送到家 | 差价 |
|---|---|---|---|
| 猪柳蛋麦满分 | ¥17.50 | ¥25.30 | **+¥7.80 (+45%)** |
| 火腿扒麦满分 | ¥11.00 | ¥18.30 | **+¥7.30 (+66%)** |
| 原味板烧鸡腿麦满分 | ¥14.50 | ¥23.30 | **+¥8.80 (+61%)** |
| 大脆鸡扒麦满分 | ¥11.00 | ¥18.30 | **+¥7.30 (+66%)** |
| 脆薯饼 | ¥8.00 | ¥16.30 | **+¥8.30 (+104%)** |
| 吉士蛋麦满分 | ¥10.00 | ¥16.80 | **+¥6.80 (+68%)** |

### 外送费用是这么构成的（`calculate-price` 原样返回）

```
脆薯饼 外送：
  productPrice        = 950   ← 商品 9.50（到店只要 8.00，本身已经加价 1.50）
  deliveryPrice       = 600   ← 配送费 ¥6.00（原价 600，无折扣）
  packingPrice        =  80   ← 打包费 ¥0.80
  discount            =   0
  price               =1630   ← 实付 ¥16.30
```

**结论：外送每单固定多付 ¥6.80（配送 ¥6.00 + 打包 ¥0.80），
再加商品本身的渠道加价（¥0.5–1.5）。**

按工作日 22 天算：**¥7.30 × 22 ≈ ¥160/月，一年约 ¥1900。**
这笔钱换来的是"不用下楼"，代价是 356 米的步行。

### 还差一个数据：起送价

单点一份 ¥16.30 的脆薯饼可以正常核价，说明**该门店外送起送门槛很低或没有**。
但真实配送门槛与运费减免规则随门店和时间变化，未做穷举，不在此下结论。

## 二、优惠券：能领到，但进不了订单

这是本次最容易被忽略、也最影响"帮你省钱"承诺的一条。

### 领到了什么

`auto-bind-coupons` 一次领取全部，5 张全成功：

| 券 | couponId | 能用于早餐吗 |
|---|---|---|
| 11.9元麦辣鸡腿堡 | `A255280326E3328D179C362B7B8DDA65` | 否，非早餐主力 |
| **免费脆薯饼** | `0D94B7923332F58026539DB8CCA81275` | **理论上可用** |
| 人气麦旋风买一送一 | `9856FF6299069479D1AC037870375F1A` | 否 |
| 9.9元中杯冰美式 | `264B97DBE02BE6CF996AA6914151C4A9` | 否，且冰饮 |
| 19.9元王牌炸鸡任选2 | `44928824D2D4273FE5ECA617BBF75483` | 否 |

### 但这张"免费脆薯饼"落不了地

三处证据链：

1. **`query-store-coupons` 不返回它。**
   查 `storeCode=1450386 / orderType=1`，只返回 3 张：
   `9.9元中杯冰美式`、`新人专享-中杯美式7折`、`新人专享-中杯奶铁7折`。
   **全部是咖啡，没有一张早餐主食券。**
2. **`calculate-price` 不会自动抵扣。**
   单点脆薯饼，返回 `originalPrice=800, discount=0, price=800` —— 还是 ¥8.00。
3. **`create-order` 根本没有传券的入口。**
   参数表里没有 `couponId` / `couponCode` / `promotionId` 任何一个字段。
   实际下单返回的 `orderDetail.couponList` 是 **`[]`**。

### 所以真实边界是

| 能力 | 能否做到 |
|---|---|
| 一键领取全部麦麦省券 | ✅ `auto-bind-coupons`，5/5 成功 |
| 查"我有哪些券" | ✅ `query-my-coupons` |
| 查"这家店这单能用哪些券" | ✅ `query-store-coupons`（会做门店/渠道校验） |
| 查询可领取的券 | ✅ `available-coupons` |
| **把券应用到订单** | ❌ **做不到** |
| **验证券能省多少钱** | ❌ **做不到**（`discount` 恒为 0） |

**正确做法：领券必须做（免费且可积累），但必须在交付时明确告诉用户
"券要在支付页手动勾选"**，不能声称"我已经帮你用券下单了"。

本项目里那句"有优惠不用是纯傻子"因此只能兑现一半：
券帮你领到手，最后一步勾选必须你亲手做。

## 三、35 个 MCP 工具 vs 产品目标：差距清单

| 产品目标 | MCP 实际能力 | 差距性质 |
|---|---|---|
| 帮你自动下早餐单 | `create-order` 可下单，返回待支付订单 | ⚠️ 半通 |
| **自动付款** | **35 个工具里没有任何支付工具** | ❌ 结构性缺失 |
| 前一晚安排好、早上直接吃 | 下单即开始 **15 分钟**支付倒计时 | ❌ 逻辑不成立 |
| 用券下单省钱 | 券无法传入订单 | ❌ 结构性缺失 |
| 记住你的口味 | 无饮食档案接口 | ⚠️ 需自建 |
| **识别三餐照片** | **MCP 不含任何视觉能力** | ❌ 靠宿主模型 |
| 算热量 | `list-nutrition-foods` 仅 160 条，无商品编码 | ⚠️ 覆盖率 29% |
| 看你过去吃过什么 | **`order-list` 可查真实订单历史** | ✅ 意外可用 |
| 送到家 | `orderType=2` 需先有 `addressId`，可新建 | ✅ 已验证 |
| 定时自动执行 | MCP 是无状态工具，不会自己触发 | ❌ 靠宿主调度 |
| 缺货自动换 | 无库存接口，只能重查菜单 | ⚠️ 事后发现 |

### 其中三条是硬伤，必须改变产品定位

**① 没有支付能力 → "全自动"不存在**

`create-order` 之后拿到的是 `payH5Url`：

```
https://m.mcd.cn/mcp/scanToPay?orderId=1030341360000795821575121269
```

这是给人扫的页面，不是给程序用的接口。**最后一步必须人来做。**
所以产品的终点只能是"预填到支付前"，不能是"替你买单"。

**② 15 分钟支付倒计时 → "前一晚下单、明早取"不成立**

实测 `createTime 10:10:04 → expirePayTime 10:25:04`。
预约的是明早 07:30，但钱必须现在付完，否则订单作废。

这个约束的后果很具体：**你想"晚上 10 点把明早的早餐定好、安心睡觉"，做不到。**
你必须在某个具体的 15 分钟窗口里完成付款。可行的做法只有：
早上出门前那 15 分钟下单支付，或者接受"预填但不支付"。

**③ 券进不了单 → 省钱承诺要打折**

见上一节。能领、能查、不能用。

## 四、每天三餐照片怎么处理

先说清一件事：**MCP 里没有任何一个工具能收照片。** 35 个工具全部是商品、门店、
订单、券、积分。照片必须由宿主（WorkBuddy 的模型）来识别，结论再写进本地账本。

### 数据流

```
你发照片
   ↓ 宿主视觉模型识别（这一步在 MCP 之外）
食物名称 + 粗估份量 + 置信度
   ↓ 按参考份量匹配营养库
热量区间（不是一个精确数字）
   ↓ 追加写入本地账本
~/.mcd-breakfast/ledger.json
```

### 照片在决策里只做三件事

| 用途 | 做法 | 不做什么 |
|---|---|---|
| 判断最近吃腻没有 | 14 天半衰期计数，近期重复的降权 | 不按"昨天吃了多少"扣减今天早餐 |
| 发现情境线索 | 「喝酒了」「没吃完」→ 记为 context | 不把一次饮酒推广成医学规则 |
| 修正偏好 | 剩菜多 → 该餐品降权 | 不因漏拍就认定你没吃 |

### 为什么照片不能当核心输入

这不是态度问题，是量级问题：

- 单张照片、无参照物、无剩菜照，中式家常菜的份量 + 油脂误差约 **±40%**
- 一份 500 kcal 的炒饭，合理区间是 **300–700**
- 而早餐可压缩的幅度只有约 **310 kcal**（760 → 450）

**误差比被控制的对象还大。** 所以"用三餐账本反推明早吃什么"在数学上不成立。
早餐必须用**独立的绝对预算 + 长期偏好**决定。

### 你没拍的时候

按设计继续跑，不追问、不催补、不当作零摄入。
主力数据不是照片，是这两个：

1. **官方营养库**（160 条，可算的 29%）
2. **`order-list` 的真实点单历史**（这条比照片可靠得多，见下）

## 五、个人记忆从哪来

四层，按可靠性从高到低：

| 层 | 载体 | 来源 | 可靠性 | 冷启动 |
|---|---|---|---|---|
| 1 | 官方订单历史 | `order-list` / `query-order` | **最高**：真实付过钱的东西 | 新账号为空 |
| 2 | 明文档案 | `data/profile.json` | 高：用户亲口说的 | 首次设置即得 |
| 3 | 追加式账本 | `~/.mcd-breakfast/ledger.json` | 中：照片估算 + 一句话 | 从零累积 |
| 4 | 情境规则 | 账本 `contexts` | 中：单次，可撤销 | 随时写入 |

### 为什么 `order-list` 是最可靠的那一层

它返回的不只是"点了什么"，而是拆解后的真实组成：

```json
{
  "orderId": "1030525170000795821281521101",
  "orderStatus": "订单已取消",
  "storeName": "麦当劳上海徐家汇餐厅",
  "orderProductList": [{
    "productName": "大脆鸡扒麦满分组合",
    "comboItemList": [
      { "name": "大脆鸡扒麦满分", "quantity": 1 },
      { "name": "鲜萃冰咖", "quantity": 1 }
    ]
  }],
  "realTotalAmount": "11.5"
}
```

**口味、份量、价格、渠道、真实组成全在里面，而且是官方记录。**
照片会错，人说会忘，这个不会。所以记忆的主干应该是它，不是照片。

代价是：新账号没有历史（本账号只有本次测试产生的 2 条）。
所以首版必须接受"前 3 次靠默认规则"，不能假装已经很懂你。

### 记忆存在哪里、怎么跨会话

放在 `~/.mcd-breakfast/`，不进仓库：

```
~/.mcd-breakfast/
├── profile.json     首次设置（预算、忌口、时间、目标）
├── ledger.json      追加式饮食账本（照片估算 + 情境 + 反馈）
└── orders.json      下单记录（orderId、金额、状态）
```

跨会话靠 `SKILL.md` 里的指令：每次开始先读这三个文件，结束前写回。
**这是 skill 而不是服务的关键限制：状态在文件里，不在云端。**
换一台机器、换一个 agent，记忆就没了 —— 除非把这三个文件同步过去。

## 六、一句话总结

> 能做的：查真实菜单与价格、算 29% 餐品的热量、领券、把订单填到支付前、
> 记住你点过什么，并把选择压缩到 1 个。
>
> 做不到的：替你付钱、把券用进订单、用三餐照片精确控热量、在你不出现的时刻自己行动。
>
> 产品必须按"能做的"来承诺。
