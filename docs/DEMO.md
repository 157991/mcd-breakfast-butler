# 演示脚本

三个必须展示的连续场景。每个场景都对应一条"普通重复下单工具做不到"的能力。

---

## 场景一：正常拍了三餐，昨晚喝了酒

**用户做什么**：把昨晚的烧烤和啤酒拍下来发过去，说一句"今晚喝酒了，明早不要冰咖啡"。

**系统做什么**：
1. 识别照片，记入账本（`photo_estimate`，误差 ±40%，不追问份量）
2. 把"喝酒"记为**当天情境**（不是永久偏好）
3. 生成明日安排时排除所有含「冰 / 冷萃 / 雪碧 / 可乐」的餐品
4. 在常点清单里挑一款，检查热量区间与预算

**输出**：

```
明早 07:30 · 麦当劳上海徐家汇餐厅 · 到店取餐柜

【大脆鸡扒麦满分组合】 约 ¥8.1 · 376 kcal
  组成：大脆鸡扒麦满分 + 小杯鲜萃咖啡

为什么是它：
  · 这个主料距上次吃 3 天
  · 在你的常点清单里
  · 前一晚饮酒，早上不安排冰饮
  · 376 kcal，在目标区间内

想换的话：大脆鸡扒麦满分、猪柳蛋麦满分组合
```

**要指出的细节**：
- 组合 ¥8.1 比单点 ¥11.5 便宜，热量只多 15 kcal —— 引擎选组合不是"消费升级"
- 这条"不冰饮"规则只在今天和明天生效，第三天自动失效

## 场景二：一整天什么都没发

**用户做什么**：什么都不做。不发照片，不回消息。

**系统做什么**：
1. **不追问、不提示补录、不把缺失当成零摄入**
2. 只降低"近期记录"的权重，不降低"长期偏好"的权重
3. 照常产出安排

**输出**：

```
明早 07:30 · 麦当劳上海徐家汇餐厅 · 到店取餐柜

【猪柳蛋麦满分组合】 约 ¥12.6 · 402 kcal
  组成：小杯鲜萃咖啡 + 猪柳蛋麦满分

为什么是它：
  · 这个主料距上次吃 5 天
  · 在你的常点清单里
  · 402 kcal，在目标区间内
```

**要指出的细节**：
- 只有 2 天记录也能工作，没有"数据不足请补充"的弹窗
- 这是与"饮食打卡应用"最直接的区别

## 场景三：临时说「明天想吃营养卷」

**用户做什么**：发一句话，不给照片。

**系统做什么**：
1. 记为 `explicit_request`，绑定到明天
2. 候选收窄到含「营养卷」的餐品
3. 仍然检查热量区间与预算 —— **优先满足不等于无条件满足**
4. 在理由里显式回显"因为你说了"

**输出**：

```
明早 07:30 · 麦当劳上海徐家汇餐厅 · 到店取餐柜

【火腿扒早安营养卷组合】 约 ¥11.7 · 459 kcal
  组成：火腿扒早安营养卷 + 小杯鲜萃咖啡

为什么是它：
  · 你说了「明天想吃营养卷」，优先按这个安排
  · 459 kcal，在目标区间内
```

**要指出的细节**：
- 如果营养卷当天全部售罄，会输出"你说的那款今天没有"，而不是静默换成别的

## 对比：为什么它不是"又一个点餐助手"

| | 普通点餐工具 | 麦麦早餐管家 |
|---|---|---|
| 每天要做什么 | 从菜单里挑 | 什么都不用做 |
| 记得你上周吃过什么 | 不记得 | 记得，且在主体名层面去重 |
| 你今天喝酒了 | 不知道 | 知道，并调整搭配 |
| 你不用它的时候 | 无法工作 | 照常安排 |
| 热量从哪来 | 不给，或给个粗略值 | 官方数据 + 套餐拆解，无数据时明说"未知" |

## 演示时可以直接跑

```bash
# 场景一
python scripts/planner.py --ledger data/ledger.normal.json  --date 2026-10-21

# 场景二
python scripts/planner.py --ledger data/ledger.sparse.json  --date 2026-10-21

# 场景三
python scripts/planner.py --ledger data/ledger.request.json --date 2026-10-21
```

加 `--json` 可以看到完整决策 trace（哪条规则排除了谁）。
