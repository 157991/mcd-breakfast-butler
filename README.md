## 它解决的不是"吃什么"，是"每天都要想一次"

按季节算，一个上班族一年要做大约 **250 次**「明早吃什么」的决策。每次 1–3 分钟，加起来十几个小时，全部花在一件结果高度重复的事情上。

现有点餐工具的问题不是推荐不准，而是**每一次都从零开始**：它不知道你上周吃过什么、昨晚喝了酒、这个月想瘦一点。所以每次都要你重新挑。

这个 Skill 换了个方向：**把决策权交出去，但保留否决权。**

| 你做的事 | 它做的事 |
|---|---|
| 随手把三餐照片丢过来 | 识别、记进账本，不要求填表、不追问 |
| 一天什么都没发 | 按长期偏好照常安排，不催、不当作你没吃饭 |
| 偶尔说「明天想吃营养卷」 | 优先满足这次要求，同时检查预算与在售 |
| 前一晚说「喝酒了，明早别给冰的」 | 把套餐里的饮品改成**去冰**，而不是把整份套餐排除掉 |
| 说一句「这个酱太冲」 | 换酱，并且记下来；下次不再给这个 |

## 它长什么样

用户每天早上只会看到一张卡片，不是一份菜单：

```
明早 07:30 · 麦当劳上海长宁福缘湾九华餐厅 · 外带

【雪菜脆笋鸡肉粥套餐】 ¥15.50 · 468 kcal
  粥 + 脆香油条 + 脆薯饼 ｜ 油条配番茄酱

为什么是它：
  · 前一晚饮酒 → 套餐里的饮品全部去冰（套餐保留，不整份排除）
  · 官方热量可算，落在 350–500 区间
  · 这个主料距上次吃 3 天
  · 不含咖啡因 —— 晚间不拖入睡

想换的话：猪柳蛋麦满分、火腿扒早安营养卷组合
```

注意卡片里为什么要写「去冰」和「配番茄酱」：这些不是装饰，是**会写进订单、店员照着做**的参数。

## 五个把设计打回重做的实测结果

我们没有先写功能再找场景，而是把麦当劳 MCP 的 35 个工具全部枚举、核心链路真机跑通，结果推翻了五个想当然的设计。**下面每个数字都能在 `evidence/` 里逐条复核。**

### ① 官方热量只覆盖 30%——而且最初的"46%"是算错的

`query-meals` 的菜单**没有任何营养字段**；`list-nutrition-foods` 是**以中文名为键的文本表、160 条、全是单品、没有商品编码**。两边键不相交，只能按名称对齐。

第一版按 `isDefault` 拆套餐，得到 46%。跑通真实下单后才发现这是假数字：

```
套餐「大脆鸡扒麦满分组合」的饮品组：
    小杯鲜萃咖啡   isDefault=1   quantity=0   ← 我按这个取
    鲜萃冰咖       isDefault=0   quantity=1   ← 订单实际给的是这个
```

订单 `1030268980…090948` 的 `comboItemList` 明确写着 **鲜萃冰咖**。

**`create-order` 认的是 `quantity>0`，不是 `isDefault=1`。** 按 `isDefault` 取，等于把冰饮当热咖啡：热量算错，而且「不要冰」这类忌口词会直接漏检——**这是一种"安静的错"，比报错危险得多。**

改成 `quantity>0` 之后的真实覆盖：

| 解析方式 | 可算热量的餐品 |
|---|---|
| 只有单品直配 | 23 / 100 = **23%** |
| 加上套餐拆解 | 30 / 100 = **30%** |

掉下来的部分不是退步，是去掉了虚高：营养库缺的正好是**冰饮系**（鲜萃冰咖、冰美式、冰奶铁、怡泉+C、美汁源），而饮品是套餐的必选项。

### ② 菜单价不是价格，按它排序会直接排反

`query-meals` 的 `currentPrice` 是「早餐卡专享价」。同一时刻用 `calculate-price` 复核：

| 餐品 | 菜单价 | 实际应付 | 偏差 |
|---|---|---|---|
| 大脆鸡扒麦满分**组合** | ¥8.1 | **¥13.50** | +67% |
| 猪柳蛋麦满分**组合** | ¥12.6 | **¥21.00** | +67% |
| 大脆鸡扒麦满分**单品** | ¥11.5 | ¥11.50 | +0% |

**组合一律 +67%，单品 0%。** 于是排序直接翻转：按菜单价，组合 ¥8.1 比单品 ¥11.5 便宜；按真实价，组合 ¥13.50 比单品 ¥11.50 贵。任何用菜单价做预算判断的逻辑，都会稳定地把用户推向更贵的东西。

所以引擎是**两段式**：菜单价只做粗筛，定案前对 top-N 逐条 `calculate-price`，用真实金额重排。

### ③ 预约不等于"延后付款"——支付只有 15 分钟

真实订单的时间戳：

```
createTime    2026-10-20 09:52:22
expirePayTime 2026-10-20 10:07:22     ← 15 分钟
reservationDate  2026-10-21 07:00     ← 取餐在明早
```

`reservationDate` 锁的只是**取餐时间**，不是付款时间。下单那一刻就开始 15 分钟倒计时，超时订单作废。

**"前一晚 22:00 自动下单、明早直接去吃"在接口层面不成立。** 可行形态只有两个：早上起床前 15 分钟内下单，或者停在下单前一步等用户点。这个 Skill 选后者，并把倒计时如实显示在卡片上。

### ④ 一句「不要冰咖啡」，必须在套餐组成上生效

这是真机下单才暴露的：用户说「今晚喝酒了，明早不要冰咖啡」，引擎却推出了「大脆鸡扒麦满分组合」。因为禁用词只匹配**商品名**，而这七个字里没有「冰」——真正含冰的是它拆出来的「鲜萃冰咖」。

**忌口与情境规则在最常见的商品形态（套餐）上系统性失效，而且失效得很安静：选出来的东西看起来完全合规。**

修法是让禁用词穿透到组成面。修好后再跑同一份账本，排除轨迹是这样的：

```
排除 大脆鸡扒麦满分组合：情境 alcohol 命中禁词「冰」
排除 猪柳蛋麦满分套餐：情境 alcohol 命中禁词「冰」
排除 火腿扒早安营养卷组合：情境 alcohol 命中禁词「冰」
…共 52 个候选被挡在门外
```

**52 个。** 一句"不要冰的"，在真实菜单上几乎砍掉一半早餐——因为绝大多数套餐默认配的都是冰咖。

但"直接排除"太粗暴了。后来查明 `modification` 提供的是**四档冰量**，正确做法是**改配而不是排除**：保留套餐，把饮品设成去冰（见 ⑤，以及 ⑥ 里"套餐内商品也能单独换"）。

### ⑤ 风味不是形容词，是三个能写进订单的参数

"选个好吃的"听起来是主观的，但在接口里它是三个具体、可传、免费的参数：

| 维度 | 实测结果 |
|---|---|
| **冰量** | 标准 / 去冰 / 多冰 / 少冰 四档，`code` 全是 `200002`，只有 `key` 不同（`0-1`/`0-0`/`0-2`/`1-1`），**+¥0** |
| **酱料** | 「蘸酱麦麦脆汁鸡」三款：北美招牌牧场酱 / 韩式烟熏芝士风味酱 / 日式鲜磨山葵酱，**+¥0** |
| **配料** | 双层吉士汉堡的吉士、酸黄瓜、洋葱粒、番茄酱、芥末酱，每项可保留（`selectedKey 0-1`）可去掉（`unselectedKey 0-0`） |

**搭配是有方向的，不是"喜欢就加"。** 这里犯过一个典型错误：按"偏好加分"给炸鸡选了牧场酱（奶香），而油炸真正需要的是酸/辛香解腻。改成偏好的加分、要避开的扣分**两边都算**之后，同一份数据改选「日式鲜磨山葵酱」。

还有一个容易漏的事实：**咖啡因不只藏在咖啡里。** 红茶是 `mid`、可乐是 `mid`、鲜萃/美式/奶铁是 `high`。只按名字里有没有"咖啡"两个字判断，会漏掉一整批，然后晚上给人送一杯红茶。

### ⑥ 套餐里那杯冰咖，可以单独换掉

先说一个反直觉的数字。默认配置下，一份早餐套餐的饮品是**鲜萃冰咖**，它加价 ¥0 —— 但它在接口里**根本没有"去冰"这个选项**。

```
鲜萃冰咖  code=521327  diffPrice=+¥0  modification=无
```

也就是说，"给你不要冰的"这句话，卡在了一杯免费但不可改的饮料上。想让饮品能去冰，必须主动把它换掉：

| 饮品方案 | 实付 | 能去冰 |
|---|---|---|
| 默认 · 鲜萃冰咖 | ¥25.50 | ✗ |
| 优品豆浆大杯（热） | ¥25.50 | 本来就不冰 |
| 可乐 / 无糖可乐 / 雪碧中杯 | **¥24.00** | ✓ |
| 阳光柠檬红茶中杯 | ¥24.00 | ✓ |
| 中杯怡泉+C | ¥25.50 | ✓ |
| 麦咖啡冰美式中杯 | ¥29.50 | ✓ |
| 麦咖啡冰美式中杯（标准冰，对照组） | ¥29.50 | — |

这张表里最重要的一行是**最后两行**：同一杯冰美式，标准冰和去冰都是 ¥29.50。

**去冰本身不改价，贵出来的钱全部来自"换饮品"。** 而且换对了还能更便宜——可乐中杯比默认冰咖低 ¥1.50。

技术上这件事能做，是因为 `rounds[].choices[]` 里**每个候选项各自带着自己的 `modification`**。
之前以为"套餐只能整份接受或整份排除"，是因为只看了套餐顶层的字段。传参走：

```
items[].roundList[].comboItemList[].modification.values[] = [{code:"200002", key:"0-0", quantity:1}]
```

于是"昨晚喝酒了，明早别给冰的"这句话，最终变成的不是砍掉 52 个候选，而是：

> 保留这份套餐，把鲜萃冰咖换成热豆浆（+¥0）。

无需 IDE、无需 MCP 宿主，直接对着 `https://mcp.mcd.cn` 发 JSON-RPC：

```bash
# 1) 放 Token（只写本地，不进仓库）
echo "YOUR_MCP_TOKEN" > scripts/.token

# 2) 看工具清单（35 个）
python scripts/mcp_call.py list

# 3) 真实链路测试：时间→账户→门店→菜单→热量→决策→核价→券
python scripts/live_test.py --store 1450034 --date 2026-10-21 --time 07:00

python scripts/resolver.py <storeCode> "2026-10-21 07:00"

python scripts/planner.py --ledger data/ledger.sparse.json   --date 2026-10-21  # 一天没拍照片
python scripts/planner.py --ledger data/ledger.request.json  --date 2026-10-21  # 临时说想吃营养卷
```

## 它怎么工作

```
拍照 / 说一句
      │
      ▼
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│ 饮食账本     │───▶│ 偏好与情境    │───▶│ 决策引擎      │
│ 官方数据/估算 │    │ 长期 + 当日   │    │ 严格优先级    │
└─────────────┘    └──────────────┘    └──────┬───────┘
                                              │
                          ┌───────────────────┴──────────────┐
                          ▼                                  ▼
                  query-meals 在售                   list-nutrition-foods
                  query-meal-detail 拆解              （按 quantity>0 拆解加总）
                  calculate-price 权威报价（分）
                          │
                          ▼
                    风味层：主风味 → 冰量 → 酱料
                    （只在真实可选项里挑，不编造）
                          │
                          ▼
                    一张卡片 → 支付前一步交给用户
```

决策优先级（严格顺序，不做加权折中）：

```
忌口/过敏 > 当日明确要求 > 情境规则 > 热量区间 > 金额预算 > 好吃 > 不重复
```

其中四条是硬约束，写在代码里而不是文档里：

- **禁用词在「商品名 + 实际组成」上匹配**，不只在商品名上匹配。
- **热量区间与金额预算前后相继、永不合并成单一分数**——否则会稳定偏向高热量。
- **组合成分未知（营养库缺件）时不假装安全**，标记"成分未验证"并降权。
- **风味只在真实存在的选项里选**——冰量、酱料、配料都来自 `query-meal-detail`，挑不到就返回空，绝不生造一个不存在的酱。

「好吃」不是形容词，它被折算成可计算的行为代理：历史出现频次 × 正向反馈 × 偏好关键词。比较一律在**主体名**层面进行 —— 把「猪柳蛋麦满分」「…组合」「…套餐」视为同一个东西，否则系统会以为"单品没吃过"而反复推单品。

**风味和"好吃"是两件事**：「好吃」决定要不要吃这个，风味决定怎么配着吃。前者靠行为数据，后者靠搭配规则（`data/flavor_rules.json`），两者的数据来源和失效方式完全不同，所以分开算。

## 明确不做的事

一个诚实的产品要写清边界，否则就会变成过度承诺：

- **不承诺减重结果。** 早餐只影响一天约 20–25% 的热量，一次夜间饮酒就能抹平一周早餐的赤字（1400 vs 1500–2000 kcal）。这里只承诺"早餐在预算内、且你愿意吃"。
- **不承诺热量精确。** 官方数据只覆盖 30% 的早餐商品，剩下 70% 显示"未知"，不拿同类均值冒充。这是数据的边界，不是算法的边界。
- **不做医学判断。** 「喝酒后不要冰咖啡」是个人偏好规则，不推广成适用于所有人的健康结论。
- **不把照片当摄入记录。** 拍到了不等于全吃完，没拍到不等于没吃。
- **不代扣款。** 订单填到支付前一步，付款必须由用户自己点。任何"帮你付了"的承诺都超出接口能力。
- **不承诺外送到家比到店便宜。** 外送已跑通（建地址 → 查门店 → 报价 → 预约下单），但它每单固定多花 **¥6.80**（配送 6.00 + 打包 0.80），再叠加商品加价，套餐类接近翻倍。按 22 个工作日算约 ¥160/月。换来的是省下 356 米，值不值要用户自己判断。
- **不承诺"前一晚下单、早上就有"。** 到店和外送的预约单**都是下单即 15 分钟支付倒计时**，预约只锁取餐时间、不锁付款时间。真实可行的形态是：前一晚算好方案存库 → 早上 06:40 由定时任务下单 → 推支付链接给用户 → 用户点一下。**早上必须点，这一步绕不过接口。**
